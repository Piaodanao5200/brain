# 写入规则

这份文件是常驻层。任何 agent 只要接入本知识库，都必须遵守。规则本身也是记忆，改它请走 supersede。

## 五条硬纪律

1. **先查后写。** 写入前必须 `kb_search` 查重。同一事实已存在就更新，不要新增第二条。
2. **分类写入。** 决策、事实、坑、待办分开存，混在一起检索会互相污染。
3. **更新而非追加。** 事实变了用 `kb_supersede`，旧条目会被标记 `superseded` 并指向新条目，**不物理删除**——"我们以前相信什么"本身是有价值的信息。
4. **必带出处与时效。** `source` 写清是文件路径、URL、PR 号还是"用户口述 @ 日期"。没有出处的记忆，可信度按 0.5 处理。
5. **禁存秘密。** 密钥、令牌、密码、私钥、手机号、身份证号一律不写。`kb lint` 会拦截。

## 该记什么

- **决策**：选了 A 而不是 B，以及为什么。三个月后有人会问这个。
- **事实**：项目里不写在代码里、但必须知道的东西（端口、分支约定、外部系统限制）。
- **坑**：踩过一次、下次不该再踩的。写清现象 → 原因 → 解法。
- **待办**：有明确下一步的事，超过 30 天没动就应该关闭。
- **知识**：外部资料的沉淀（协议规范、API 限制、基准数据），带来源链接。

## 不该记什么

- 代码里能直接读到的（函数签名、目录结构）——去读代码。
- 一次性的对话细节、寒暄、"用户让我写个函数"。
- 未经核实的猜测。要记就标 `confidence: 0.5` 并写明"未验证"。
- 别人的隐私、客户数据、内部链接口令。

## 条目格式

正文 50–150 字，第一句就是结论。结构建议：

```
结论一句话。

依据：具体数据 / 文件路径 / 复现步骤。
边界：什么情况下这条不适用。
```

超过 1200 字的条目应该拆开——单条正文越长，检索命中后注入的噪音越大。

## 冲突怎么处理

发现新信息与已有条目矛盾时，三选一，不要两条都留着：

- **新信息更可靠** → `kb_supersede`，旧条目自动失效
- **不确定哪个对** → 两条都保留，但都标 `confidence: 0.5`，并在正文写明"存在冲突，待验证"
- **需要人判断** → 写一条 `todo`，在对话里直接问用户

## 权威顺序

**代码 > 记忆。** 记忆与代码冲突时，正确动作是去看代码，然后修掉那条记忆。

**用户当前的话 > 历史记忆。** 用户这轮说"改成 MySQL"，不要拿三个月前"用 Postgres"的条目去反驳他，直接更新记忆。

## 与其他 agent 协作

- 写入时 `source` 写明是哪个 agent 写的（如 `claude-code @ 2026-11-15`）。
- 不确定别的 agent 是否已经记过，先 `kb_search` 一遍再下手。
- 不要修改别人写的条目正文，用 `kb_supersede` 追加你的版本，保留演化链。
