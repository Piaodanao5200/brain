## 结论

记忆与知识以「一个条目一个 .md 文件」的形式存在 `vault/` 下，文件系统就是数据库，检索用 BM25（中文二元切分），不引入向量数据库。

## 为什么

- **可读可改**：用户要实时查看和更新，纯文本加任意编辑器或 Obsidian 就能做到，不需要管理后台。
- **可版本化**：git 直接管，谁在什么时候写了哪条、改了什么，天然有历史。这是审计和回滚的前提。
- **零运维**：没有数据库进程、没有 embedding 服务、没有迁移脚本。个人和小团队规模下向量库的召回提升远小于它的运维成本。
- **可迁移**：任何 agent、任何语言都能直接读文件，不被某个产品的 SDK 绑死。

## 代价

- 语义检索弱于向量：同义不同词的查询会漏。缓解办法是标签 + 标题规范 + 必要时后续加一层 embedding 索引作为**旁路**，而不是替换真源。
- 条目上千后需要分片和索引维护，目前规模（几十到几百条）不构成问题。

## 什么情况下应该推翻

条目超过约 2000 条、或出现大量"描述性长文本"（如会议记录）导致 BM25 召回明显下降时，加向量索引。注意：只加检索层，真源仍然是 Markdown。
