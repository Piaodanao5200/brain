## 这本书在讲什么

这不是一本观点书，而是一本**任务驱动的技术手册**——它没有贯穿全书的作者论证链，而是按功能域把"怎么把一台 S7-1200 用起来并稳定跑下去"拆成装、配、编、调、查、通信六件事，供工程师按需查阅。一句话主旨：把 S7-1200 PLC 从硬件安装、程序构建、指令使用到通信组态与在线诊断的完整操作方法，组织成可按需查阅的任务指南。

全书 15 个正文章可归为 5 大功能域，层层深入又彼此支撑：**基础认知域**（产品、安装、功率）铺底；**核心原理域**（PLC 概念、编程概念）是理论内核，后面所有操作都建立其上；**指令域**（基本/扩展/工艺指令，约 660 页）是最大的参考区；**通信与互连域**（PROFINET/PROFIBUS/PtP/Modbus）并列展开；**运维域**（在线诊断、技术规范、功率、更换）贯穿前四项。作者要回答的核心问题很朴素：让工程师用一台 S7-1200 完成一个自动化项目——从选型安装、写程序、配通信，到上线后排障。

## 一、基础认知域：把 PLC 装起来、算清楚电（ch1–4）

这一域铺垫三件事：S7-1200 是什么、怎么装、功率怎么算。它们看起来是"开工前的杂事"，但手册把其中若干条写成了必须遵守的硬约束——因为安装与供电的错误会在多年后以最不可预测的方式回来找你。

### 从零开始的七步设计法

**它解决什么问题**：面对一台新机器，先做什么后做什么，才不会在写到一半时发现安全回路没做、模块选错、符号表要推翻重来。

**核心逻辑**：手册把系统设计拆成有序的七步——分区 → 功能规范 → 安全电路 → 系统安全 → 操作员站 → 组态图 → 符号表。关键不在"列清单"，而在**依赖顺序与安全贯穿**：功能规范未定就选模块、没做安全分析就写联锁，后面每一步都会返工。手册尤其强调，安全电路要在 PLC 程序之前独立画出来，而不是事后补进用户程序；它明确警告这份设计指南"仅用于设计正常和预期的异常操作"，不能当成完整的安全方案。

**书中的用法**：ch7.1 表 7-1（p199–200）以一台机器的完整设计贯穿七步，并给出"安全贯穿原则"；手册在同一处提醒，安全电路的具体细节必须参照公司规范，并留出独立于 PLC 的急停/机电超控。这是一张**顺序依赖图**，不是可勾选的行政流程。

> "此信息仅用于设计正常和预期的异常操作。出于安全考虑，不应依赖此'最佳情况'方案。"（p199）

**什么时候会失效**：它只给骨架，不含具体计算与参数；安全电路细节交公司安全规范，照抄这张表不等于完成安全设计。

### 功率预算：把"带不带得动"变成一道算术题

**它解决什么问题**：手上有一份 CPU + 模块清单，5V/24V 两路电源够不够？要不要加电源？加了会不会出问题？

**核心逻辑**：S7-1200 的 CPU 提供两路相互独立、有硬上限的预算——5V 供 CPU 自身与扩展模块总线，24V 传感器电源供本地输入点与继电器线圈。方法分三步：先查该 CPU 型号的两路预算值与最大模块数；再把每个 SM/CM/SB 的 5V 需求、每个 24V 输入点（按 4 mA/点）与继电器线圈（按 11 mA/点）逐项累加；最后分别相减得到两路差额。**5V 差额为负时没有"外挂 5V"这个选项**，只能拆模块或换更大 CPU；24V 差额为负时可以加独立外部 24V 电源，但绝不能并到 CPU 传感器电源上——两个电源各自试图建立自己的电压，会形成环流与拉锯，导致寿命缩短、立即故障或系统运行不确定。所有非隔离 M 端子必须接到同一参考电位；内部继电器线圈功率已计入 CPU 预算，不要重复计算。

**书中的用法**：附录 B 表 B-1（p1781–1782）给出完整算例：CPU 1214C AC/DC/继电器（5V 预算 1600 mA、24V 预算 400 mA）+ 1×SB1223 + 1×CM1241 + 3×SM1223 + 1×SM1221，共 48 入 36 出。5V 需求 = 50 + 220 + 3×145 + 105 = **810 mA**，差额 **790 mA（充足）**；24V 需求 = 56 + 8 + 96 + 264 + 32 = **456 mA**，差额 **−56 mA**，须加至少 56 mA 的独立外部 24V 电源，且不得与传感器电源并联。表 B-2 给出空白模板供照此复算。

> "将外部 24V DC 电源与 DC 传感器电源并联会导致这两个电源之间有冲突……该冲突可能使其中一个电源或两个电源的寿命缩短或立即出现故障，从而导致 PLC 系统的运行不确定。"（p61；附录 B p1781）

**什么时候会失效**：更多模块型号的具体需求须回附录 A 逐查，数值以模块实际额定范围为准；任何组态变更都要重新核算，不能沿用旧余量。

### 安装接线：把经验性规范固化成清单

**它解决什么问题**：怎么把 PLC 装进柜子、接地、接线，才不被粉尘、过热、传导干扰和电气故障拖垮，并留出独立于 PLC 的安全兜底。

**核心逻辑**：这一域把"老师傅经验"写成了可核对的硬规则：上下与前端各留 ≥25 mm 散热间隙（垂直安装时环境温度上限再降 10°C）；开放式设备必须装在 IP54 等封闭外壳内且仅授权人员开启；高压高噪声设备与低压逻辑设备物理隔离，低压信号线不得与交流动力线同槽；接线前断开所有相关设备电源并配独立急停；单点接地、地线短且 ≥2 mm²；感性负载跨接抑制电路（AC 用 MOV、DC 用二极管 + 稳压管），灯负载加浪涌限制；所有非隔离 M 端子接同一参考电位。这些规则看似琐碎，却把"电气故障与意外机械动作"这一最高等级风险挡在门外。

**书中的用法**：ch4.4（p81–87）给出"隔离开关 + 过流保护 + 浪涌抑制 + 屏蔽单端接地 + 合适线径"的接线清单；手册在 p85–86 特别指出，钨灯冷态接通浪涌是稳态电流的 10–15 倍，频繁开关会烧蚀继电器触点，应加可更换的插入式继电器或浪涌限制器。

**什么时候会失效**：手册假设读者具备基本电工素养；真实的接地工艺、抗干扰布线、网络拓扑规划等经验性知识并不在书中，这份清单是底线而非充分条件。

→ 深入：[安装接线与安全兜底规范](./dist/s7-1200/references/capabilities/power-wiring-installation.md)

## 二、核心原理域：用户程序到底怎么跑（ch5、ch7）

这是全书的理论内核，后面所有操作都建立其上。如果只记住这个域的两句话，那就是：**OB 是事件入口而不是函数，FB 靠背景 DB 实现"实例"**。这两点理解错了，写出来的程序会在最意想不到的地方丢数据或错响应。

### 程序结构决策：OB / FC / FB / DB 各司其职

**它解决什么问题**：每一段逻辑该放进哪种块？多个同类设备怎么写才能互不干扰、还能复用？

**核心逻辑**：四类块按角色分工。OB 由事件驱动、由操作系统调度，是带编号、启动事件与优先级的**事件入口**——它不是可互相调用的子程序，OB 之间及被 FC/FB 调用均不允许。FC 不带背景 DB，用局部数据堆栈、临时数据块结束即丢失，适合无状态的可复用运算。FB 带背景 DB，参数与静态数据跨扫描保留；**同一个 FB 配不同背景 DB 就是不同"实例"**，可控制多台设备而互不干扰。DB 是存储区，分全局（所有块可访问）与背景（绑定 FB 实例）。结构上先决定线性还是模块化：有复用需求就选模块化，把一个 FB 存进项目库。调用有硬边界：从循环/启动 OB 出发最多嵌套 16 层，从中断 OB 出发最多 6 层。

**书中的用法**：c09（p217）展示项目变量表中的 Start/On 如何对应 SCL 声明表里的 StartStopSwitch/RunYesNo，把 Input/Output/InOut/Static/Temp/Constant 这六类块接口与实际调用参数对应起来；ch7.3.4（p207）则给出"一个 FB 配多个背景 DB"的落地模式——3 台电机各用一个背景 DB 存自己的速度、加速时间与运行时间。

> "调用带有不同背景数据块的同一 FB 不会对其它任何背景数据块的数据值产生影响。"（p206）

**什么时候会失效**：背景 DB 并非访问隔离，手册明确"任何代码块都可访问背景 DB 中的数据"，多设备串扰的根因常常就是复用了同一个背景 DB；误把 OB 当子程序调用会直接违反调度模型。

→ 深入：[用户程序结构决策（OB / FC / FB / DB）](./dist/s7-1200/references/capabilities/program-structure-decision.md)

### 扫描周期、实时性与中断

**它解决什么问题**：一个输出点从输入变化到响应要多久？周期任务该挂哪个 OB？时间超限会怎样？

**核心逻辑**：每个周期按"写输出 → 读输入 → 执行用户程序 → 后台处理"推进，这个扫描周期是确定性的实时单位，但会被更高优先级事件在任何阶段打断。优先级 1–26，1 是主程序循环、26 最高；事件会排队且有未决上限，达到上限后下一个事件将丢失，溢出由时间错误 OB（OB80）响应。周期任务用循环中断 OB（最多 4 个、一事件一 OB、用相移错开以免同时抢占），不能什么都塞进 OB1。CPU 强制监视最大扫描周期（1–6000 ms，默认 150 ms）：首次超时只写诊断缓冲区、CPU 仍保持 RUN，但同一周期第二次超时强制进 STOP。因此实时性估算 = 最多一个扫描周期 + 中断等待延迟。

**书中的用法**：ch5.1.2（p97）用 ①–⑤ 步拆解完整扫描时序，并以"输出点从输入变化到响应的延迟"为分析对象，结论正是"最多一个扫描周期 + 中断等待延迟"。时钟存储器位映射表（ch5.1.6 表 5-20，p123）给出位 0–7 的周期/频率（位 3 = 0.5 s/2 Hz，位 7 = 2.0 s/0.5 Hz），用于不值得动用中断的简单周期触发。

> "达到未决事件限值后，下一个事件将丢失。"（p116）

**什么时候会失效**：频率高于扫描速率的事件用普通指令会严重漏计，必须改用 HSC；从 V3 迁移到 V4 时，OB 默认不可中断，须复核中断属性，否则高优先级 OB 无法抢占（见"陷阱"节 ce29）。

→ 深入：[扫描周期、实时性与中断组态](./dist/s7-1200/references/capabilities/realtime-scan-interrupt.md)

### 数据类型与寻址：过程映像、:P 与优化 DB

**它解决什么问题**：变量放哪个区、地址怎么写、为什么程序读到的值总慢半拍或对不上？

**核心逻辑**：最容易出错的地方是**过程映像与立即访问的区分**。普通 I/Q 访问的是周期初刷新、周期末写回的快照，最多带来一个扫描周期延迟；要立即访问物理点就加 `:P` 后缀——`I_:P` 只读且不更新输入映像，`Q_:P` 只写但同时改变输出映像，而强制只能强制 `:P` 外设。存储分三级：装载存储器≈硬盘（非易失，存程序/组态）、工作存储器≈RAM（易失，存当前值）、保持性存储器（非易失，存限量运行值）。优化 DB 的元素只有符号名、无固定绝对地址（新 DB 默认优化）；凡是需要绝对寻址的场合（Modbus DATA_PTR、Variant 的 STRUCT 实参、CTRL_HSC_EXT 起始值、DPRD_DAT）都必须显式改成标准访问。数据类型的硬约束也要记牢：Real 只有约 6 位有效数字，Int 范围 −32768~32767，超范围要换 DInt/LReal。

**书中的用法**：c04（p138）用浮点演算点破精度边界——"100 000 000 + 1 = 100 000 000"，小量被大数吃掉；c05（p146）演示 `ARRAY[1..20] of REAL` 的声明与用变量下标寻址（i=3、j=4 → ARRAY3[3,4]）；c07（p222–223）用 PEEK 按区域码（16#84 = DB、16#81 = 输入映像）加字节偏移量读写，明确规定须用标准未优化 DB。

> "如果数字相差 10 的 x 次方，其中 x > 6 (Real) 或 15 (LReal)，则会发生上述情况。例如 (Real)：100 000 000 + 1 = 100 000 000."（p138）

**什么时候会失效**：沿用默认优化 DB 去做需绝对寻址的操作会报"无绝对地址"类错误，这是高频坑；保持性只覆盖显式标记的变量，未设保持的累计量、配方上电即丢。

→ 深入：[数据类型与寻址规则](./dist/s7-1200/references/capabilities/data-types-addressing.md)

### 数据一致性：让多个值"同时正确"

**它解决什么问题**：几个相关的值（如设定值、实际值、状态字）怎么保证是被同一时刻读到的，而不是"半新半旧"？

**核心逻辑**：CPU 只保证**单个基本数据类型**读写的原子性，不保证跨多个值的复合一致性——中断 OB 或 HMI 通信会周期性地插进来改掉其中一部分。手册给出的三段式临界区是 `DIS_AIRT → 读写多个值 → EN_AIRT`：把这段时间内的中断延迟掉，保证几个值在同一扫描周期内一致。配对规则很严格：每次 DIS_AIRT 都必须由一次 EN_AIRT 抵消，且 EN_AIRT 必须在同一 OB 或其调用链内执行、RET_VAL=0 才算真正恢复。多字节外围数据则用 DPRD_DAT/DPWR_DAT 一致性指令整体搬运（PROFINET 最多支持 1024 字节一致性数据，一致性外围 I/O 仅支持 1、2、4 字节），并须把这些数据从过程映像自动更新中删除。

**书中的用法**：ch7.4（p213）直接给出反例场景——HMI 画面上显示的一组值可能来自 CPU 的不同扫描周期，这正是"画面值对不上"的机制；c12（p295）的 Deserialize 示例演示先 MOVE 清零 `#BufferPos`，再把 Buffer DB 中顺序排列的客户数据反序列化写入 Target DB，是顺序数据搬运的典型场景。

> "如果用户程序共享存储器中在程序循环 OB 和中断 OB 之间生成的多个值，用户程序还必须确保在修改或读取这些值时保持一致性。"（p213）

**什么时候会失效**：DIS_AIRT 会推迟中断，增大事件到 OB 的等待时间，临界区不能长；EN_AIRT 漏配对或放错 OB 会让中断被长期禁用，高优先级事件得不到响应。

→ 深入：[数据一致性保障](./dist/s7-1200/references/capabilities/data-consistency.md)

## 三、指令与工艺域：当普通指令跟不上外部世界（ch8–10）

这是全书占比最大的一域（p243–904，约 660 页），也是蒸馏时最克制的一域：几百条指令的参数表适合检索，不适合当方法论。真正值得单列的是 ch10 的工艺部分——它回答一个常见问题：**当被控事件的频率超过 PLC 扫描速率时，怎么办？**

### 工艺对象与高速计数 / PID / 运动控制

**它解决什么问题**：编码器脉冲比扫描周期还快、轴要恒速平稳、温度要稳住——普通计数器和主循环里的 PID 不够用，怎么办？

**核心逻辑**：以**工艺对象（TO）**为入口封装轴、PID 等功能，参数保存在专属 TO-DB，由系统 OB 驱动，必须通过项目树添加并下载（重命名后须在 STOP 重新下载以保证一致性）。三条选型线：其一，事件频率高于扫描速率就用 HSC——硬件实现，下载组态后无需调用指令即开始计数，并按同步/门/捕获/比较四类功能组合，配合软件门 × 硬件门 → 内部门状态表控制何时计数。其二，开环轴用 PTO（板载或信号板高速输出，可用轴数受 CPU 型号限制），闭环则用模拟量 I/O 或 PROFIdrive。其三，PID 必须在恒定采样间隔下运算，应放进循环中断 OB 而不是 OB1，调试走"测量 → 预调节/精确调节 → 上传参数 → 验证"。

**书中的用法**：c16（p746）给出 CPU 1217C 板载差分输出的四种 PTO 速度组合（1 MHz×4 / 1 MHz+100 kHz+20 kHz / 200 kHz×4 / 100 kHz×2+200 kHz×2），直观展示轴数受输出资源约束；c15（p720–721）演示 PID_Temp 串级：主站 PID_Temp_1 的 OutputHeat/Slave 接从站 PID_Temp_2 的 Setpoint/Master；c17（p777）则逐步演示经消息帧 4 组态 SINAMICS S120 驱动器与编码器。

> "基本计数器指令限于低于扫描速率的计数事件。HSC 提供高于 PLC 扫描速率的计数脉冲……下载硬件组态后，HSC 无需任何调用指令即可计数。"（p631–632）

**什么时候会失效**：增量编码器不能当绝对值编码器用，TO 与驱动器的报文/电机/最大速度不一致会在启动时报错（见"陷阱"节 ce35、ce36）；把 PID 挂在 OB1 每周期算，采样时间抖动会被误当作过程响应，整定必然失败。

→ 深入：[高速计数 / PID / 运动控制工艺组态](./dist/s7-1200/references/capabilities/technology-motion-config.md)

## 四、通信与互连域：选对协议，还要选对角色（ch11–14）

PROFINET、PROFIBUS、PtP、Modbus、Web 服务器、邮件并行展开。这一域的核心问题不是"指令怎么调"，而是"选哪个协议、设备扮演什么角色、怎么组态才不留隐性故障"。

### 通信协议选型与连接组态

**它解决什么问题**：设备间怎么连？PROFINET 里设备该当普通 IO 设备还是智能设备？Modbus 谁主谁从？连不上又从哪查？

**核心逻辑**：PROFINET 先分角色——IO 控制器 / IO 设备是确定角色，设备须先分配名称才能连接；"智能设备（I-Device）"是既具备自身用户程序预处理、又作为 IO 设备挂到上位控制器的双重角色，通过 GSD 文件（而非 STEP 7 项目）向上位站暴露接口，从而保护专有知识——把它当普通 IO 设备会白白丢掉预处理和知识保护价值。共享设备是"把物理设备的子模块独占分配给不同控制器"，访问权、发送时钟、IP 必须跨项目一致。连接建立在物理与逻辑两层组态，三要素齐备且伙伴已创建。Modbus 则先定主从角色、再选功能码（读保持寄存器用 03）。PUT/GET 访问默认禁用，须显式启用，而且"设了密码"不等于"禁止通信访问"。

**书中的用法**：c19（p1341–1342）演示 MB_SERVER 建立两个 TCP 连接，各用独立背景 DB、连接 ID 与端口（连接 1：ID=1/LocalPort=502；连接 2：ID=2/LocalPort=503），RemoteAddress 设为 0.0.0.0 时响应所有客户端；c18（p1024–1025）用 T_CONFIG 在运行时改 IP/掩码/网关，前置条件是 CPU 属性里勾选"在设备上直接设置 IP 地址"；c20（p1373–1374）给出 Modbus RTU 主站四段式：首扫描用 Comm_Load 组态 RS485 端口 → Modbus_Master 从从站 #2 的 400001 读 100 字到 MW500–MW698 → 处理 DONE/错误 → 写回数据。

> "PLC 到 PLC 通信（使用代码块中的通信指令）不受 CPU 中安全等级的限制。"（p226）

**什么时候会失效**：PROFIBUS 的 step-by-step 组态流程在本次蒸馏中是轻缺口——物理层 RS485 端接规则（仅两端设备置 On 端接偏置，中间置 Off）已覆盖，但没有独立验证通过的完整组态流程。RS485 总线若多点端接会引起信号反射；只靠 CPU 密码保护无法约束程序内的通信指令。

→ 深入：[通信协议选型与组态](./dist/s7-1200/references/capabilities/communication-config.md)

## 五、运维域：用起来，还要稳定跑下去（ch15 + 附录）

这是贯穿全域的一章：查故障、下载调试、算功率、选型号、换设备、做维护。手册在这里给出的不是技巧，而是一条条"排障取证顺序"和"高风险动作的硬前提"。

### 在线诊断与故障排查：从 LED 到诊断缓冲区

**它解决什么问题**：CPU 停了、报错了、输出不对，第一步该看哪里，第二步又看哪里？

**核心逻辑**：排障有固定的取证顺序：先看 CPU 三灯组合判据 → 转到在线、连接 CPU → 读**诊断缓冲区（第一现场）** → 按事件类型映射到对应错误 OB（时间错误 OB 用 fault_id 判据；诊断错误 OB 缺失时 CPU 会忽略错误并保持 RUN；拔插模块时分布式 I/O 保持 RUN、中央机架一律 STOP）→ 用诊断指令按粒度递进（DeviceStates/ModuleStates 看整体，Get_Name/IP 定位，GET_DIAG/RD_SINFO 读细节）→ 间歇性问题用 Trace 高速记录（需 SIMATIC 卡 ≥1 MB）。关键认知是：很多错误"默认只记一条诊断、CPU 仍 RUN"，属于静默故障，不主动查就永远发现不了。诊断缓冲区本身是最多 50 条、仅 10 条永久、满后覆盖最早、掉电保存、MRES 也不清除的环形缓冲。

**书中的用法**：c10（p525–530）构造 16 个 PROFINET 从站，MODE 2 返回 `0x0300_0000` 表示设备 1 故障，MODE 4 返回 `0xFDFF_0100` 表示设备 12 不存在；c11（p532–538）在含 18 个 I/O 模块的从站上，MODE 2 返回 `0x0180_0000`，逐位解析出仅模块 15 故障。对"模拟量返回 32767 到底是断线还是溢出"这类歧义值，手册在 p1524–1527 给出的路径是：建诊断错误 OB → 调 RALRM(F_ID=LADDR) → 解析 AINFO 字节 26–33（16#0001 短路 / 0006 断线 / 0007 超上限）。

> "部分安全事件会在诊断缓冲区中生成重复条目。这些消息可能会堵塞诊断缓冲区，从而可能阻碍其它事件消息。"（p124）

**什么时候会失效**：诊断缓冲区是覆盖式的，高频重复事件会把关键线索冲掉（可组态限定安全事件消息数量）；日时钟默认值不可信，断电超期后时间戳会错乱——依赖时间戳追溯前必须先设置时钟。

→ 深入：[在线诊断与故障排查](./dist/s7-1200/references/capabilities/online-troubleshooting.md)

### 下载、调试与在线同步：别把现场改动当作可以随手覆盖

**它解决什么问题**：程序怎么下进去、下失败怎么恢复、现场被改过的值怎么不被盲目冲掉？

**核心逻辑**：下载前先判兼容——按工作存储器容量与 I/O 兼容两条判据，组态 1215C 却实际连 1212C 就不允许下载，须"更改设备"修复。在线/离线不一致时先比较再定同步方向，别默认用项目覆盖现场。监视、修改、强制三者能力不同：监视只读、修改仅临时改值、强制把值锁存在 CPU 中且只能强制 `:P` 外设——强制值随项目与存储卡传播，关掉 STEP 7 仍继续生效。RUN 模式下载要格外小心：改动立即作用于真实过程，一次超过 20 个块必须切 STOP；删除输出逻辑后，输出在下一次上电循环或 STOP 前仍保持最后状态。DB 的在线值可以捕获快照，再恢复为起始值或初始值。

**书中的用法**：f33（p235）给出下载失败的升级路径——报 16#02:4175 时先修正、重试，多次失败则清空装载存储器/复位出厂再重下；f36（p239、p1500）的能力矩阵明确"唯一能强制的是强制表格，且只能强制 :P 外设输入"；f63（p1516–1518）演示 RUN 下给 DB 加变量且不重新初始化：启用"下载而不重新初始化" → 在预留区（默认 100 字节）内加变量 → 下载后旧值保留、新变量取起始值。

> "在强制表格中强制输入或输出时，强制操作将变成项目组态的一部分。如果关闭 STEP 7，被强制元素仍会在 CPU 程序中保持激活状态，直至这些元素被清除。"（p1508–1509）

**什么时候会失效**：强制是现场安全事故的常见来源，调试结束必须显式"停止强制"；STOP 模式下启用输出不等于安全，须先确认不会导致意外设备动作；RUN 下载期间 WRIT_DBL 等报 80C0/82C0 是临时错误，应稍后重试而不是当永久故障排查。

→ 深入：[程序下载、调试与在线同步](./dist/s7-1200/references/capabilities/program-download-debug.md)

### 存储卡、固件与出厂复位维护

**它解决什么问题**：程序怎么批量灌给多台 CPU？固件怎么升？忘了密码、要清数据、要做备份，各走哪条路？

**核心逻辑**：三类卡分用途——传送卡灌完程序要取出、程序卡作为外部装载存储器必须常驻（取出即 STOP）、固件更新卡靠卡根的 FWUPDATE.S7S 文件触发。插卡前 CPU 必须在 STOP：向运行中的 CPU 插卡会立即切 STOP、可能中断过程。要分清暖启动与存储器复位（MRES）：暖启动保留保持性数据、只初始化非保持数据；MRES 清除所有工作/保持/非保持区并把装载存储器复制到工作存储器，但**不清除诊断缓冲区和永久 IP**。备份则按需求选方式：只要恢复 DB 实际值，用可编辑的监视值快照；要完整恢复则用"从在线设备备份"（仅 STOP 可行、不可编辑）。

**书中的用法**：f22（p162–164）把刷固件固化为可核对流程——解压 zip 到卡根生成 FWUPDATE.S7S → 确认 CPU 空闲后插卡 → 全程保持 24V 等 LED 完成 → 取卡重启；f19（p156–157）制作传送卡时勿删 `__LOG__` 与 `crdinfo.bin` 隐藏文件；f24（p165）忘记密码时用空传送卡擦除内部装载存储器，再从 STEP 7 下载新程序——代价是原程序不可恢复。

> "如果使用 Microsoft Windows 的格式化程序重新格式化了 Siemens 存储卡，那么 S7-1200 CPU 将无法再使用该存储卡。"（p162）

**什么时候会失效**：格式化存储卡后不能直接切 RUN，须"移卡重启"或"不移卡重启"二选一；固件更新完必须用新固件启动模块，否则旧固件仍激活；跨大版本不能从 V3.0 一步升到 V4.x。

→ 深入：[存储卡、固件与出厂复位维护](./dist/s7-1200/references/capabilities/storage-firmware-maintenance.md)

### 设备更换与版本兼容：单向的 V3.0 → V4.2

**它解决什么问题**：老 CPU 坏了要换新型号，项目、程序、模块、HMI 怎么迁？换完还能退回去吗？

**核心逻辑**：先定方向——更换只支持 V3.0 → V4.2 的硬件替换，不是固件升级，而且**下载组态后 V4.2 不可换回 V3.0**，所以更换前必须先归档 V3.0 项目。然后是七步核对：升级项目（STEP 7 V11/V12 先升 V13 SP1 再升 V14，禁止从旧版直接复制粘贴逻辑，须整项目升级后编辑）→ 核对兼容项（密码保护级别映射、OB 中断属性——V3 默认不可中断、传送卡不兼容须重建 V4.2 卡、GET/PUT 默认启用）→ 运动控制（V1/V2 库由编译替换为 V3 指令，TO 不自动升级须手动选 V5.0，核对轴参数字段重命名）→ HMI 重新编译下载 → DB 预留区（V4.0+ 每个 DB 增 100 字节，下载前在选项设置里把预留设 0 或逐 DB 删除）→ 解除专有技术/序列号复制保护 → 重新编译全部块、纠正所有错误后下载。

**书中的用法**：附录 D.1（p1799–1806）给出完整更换决策与兼容检查流程。一个典型输入是：某 V3.0 项目（STEP 7 V12）含 HMI + 运动控制 V3.0 TO + 专有技术保护块——按顺序 V12→V13 SP1→V14 整项目升级，核对密码映射与 OB 属性，TO 手动升 V5.0 并处理字段重命名，HMI 重编译下载，解除保护后重新编译全部块；下载前可撤消，下载后不可回退。

> "版本 3.0 程序传送卡与版本 S7-1200 V4.0 CPU 不兼容。插入含有 V3.0 程序的存储卡会导致 CPU 错误。"（p152/157）

**什么时候会失效**：这条流程仅针对 V3.0→V4.2；V4.0/V4.1 项目可直接在 V4.2 运行、无需修改；纯订货号与端子排套件对照属于查阅表，走检索而不在此流程内。

## 陷阱与反例

手册用大量"警告/小心"框标出了失败模式。下面挑六条最有杀伤力的，讲清**陷阱 → 机制 → 预警信号**。

**1. 把外部 24V 电源并到 CPU 传感器电源上**（ce03，p61）。*陷阱*：24V 传感器电源带不动所有输入点，于是"再并一个 24V 电源"。*机制*：两个电源都试图建立自己偏好的输出电压，并联后形成环流与电压拉锯，结果可能是寿命缩短、立即故障或系统运行不确定——不是"多一路电"，而是两个稳压源互相打架。*预警信号*：正极被接在一起、预算不够时第一反应是"补一个并联电源"。正确做法是两路分别给不同位置供电，仅共 M。

**2. 把 PLC 当成唯一的安全屏障**（ce10，p81/p199）。*陷阱*：安全联锁只写在用户程序里，认为"程序里已经停机了"。*机制*：PLC 的单点故障（CPU、电源、I/O、程序跑飞）会同时击穿"检测—决策—执行"整条链，而且手册明确电子控制设备可能失灵并导致意外动作。*预警信号*：没有硬件急停回路、风险评估把一台非 failsafe 型号当"安全 PLC"。必须保留独立于 PLC 的急停/机电超控/冗余安全功能。

**3. 忘记强制值会持续生效并传播**（ce24，p1508–1509）。*陷阱*：调试时强制了 I/O，结束后关掉 STEP 7 就以为没事。*机制*：强制值存在 CPU 里而非监视表格里，成为项目组态的一部分，并经存储卡装载到其他 CPU 后继续强制——"关掉软件就复位"的直觉完全错误。*预警信号*：调试结束没点"停止强制"、现场输出行为与程序逻辑对不上、把带强制点的程序复制到别的 CPU。

**4. 把"基本数据类型一致"误推为"多个值一致"**（ce32，p213）。*陷阱*：听说"CPU 保证数据一致性"，就把几个相关变量分散读写。*机制*：CPU 只保证单个基本类型的原子性；中断 OB 或 HMI 通信会插进来改掉其中一部分，读到来自不同扫描周期的"撕裂"组合。*预警信号*：HMI 画面显示的值"对不上"、多个相关值在循环 OB 与中断 OB 间共享却没有 DIS_AIRT/EN_AIRT 保护。

**5. 误把 RUN 模式下载当成无风险的"小改动"**（ce25，p1510）。*陷阱*：以为在线下载"对过程干扰最小"就随手改。*机制*：改动立即作用于真实过程；更隐蔽的是 STEP 7 在 CPU 处于 RUN 且有程序更改时默认优先尝试 RUN 模式下载，除非主动切到 STOP。*预警信号*：未评估对操作员与机器的安全后果、一次下载超过 20 个块仍在线改、以为"只改一个参数"不会立即影响输出。

**6. 把 PID 放在主循环 OB1 每个周期都算**（ce34，p666）。*陷阱*：图省事把 PID 块直接挂 OB1。*机制*：PID 算法假设固定采样周期并监视两次调用的间隔，而 OB1 周期随通信负荷与程序波动变化，采样时间抖动会被误当作过程响应，破坏 P/I/D 计算、引起振荡。*预警信号*：PID 块挂在 OB1、采样时间监视告警（warning 0020）、控制输出波动与扫描周期相关。正解是放进循环中断 OB 获得恒定采样。

4. **"手册是查阅工具，不是方法论"这一反对意见是成立的**：把它蒸成 skill 确有过度抽象的风险。这本 DIGEST 因此只呈现决策型/流程型/计算型内容，而不是宣称覆盖了全书；把它当"可操作决策的再呈现"，而非全书的替代品。

## 关键术语速查

| 术语 | 作者的用法 | 和常识的差异 |
|---|---|---|
| OB（组织块） | 定义程序结构，充当 OS 与用户程序接口，由事件驱动（p89、p204） | ≠ 主函数/main()，是带编号、启动事件与优先级的事件入口，OB 不可互调 |
| FC（功能） | 无背景 DB、用局部数据堆栈，临时数据不保存（p205） | ≠ 通用编程的函数，是无状态、跨扫描不留数据的运算块 |
| FB（功能块）与实例 | 用背景 DB 保存调用实例数据，不同背景 DB 互不干扰（p89、p206） | "实例 = 一次调用 + 专属背景 DB"，是 S7 的复用核心，不是普通函数 |
| 背景 DB（Instance DB） | 存储特定 FB 的数据，结构反映 FB 接口（p207） | ≠ 私有数据，任何代码块都可访问；串扰常因复用同一背景 DB |
| 扫描周期 | 写输出→读输入→执行程序→后台处理，可被更高优先级事件打断（p89、p97） | ≠ 固定频率的循环，是确定性实时单位，耗时随负载变化 |
| 过程映像 | 周期初读输入到映像、周期末写输出到物理点（p97、p127） | ≠ 直接读写物理 I/O，普通 I/Q 访问的是快照，最多延迟一个周期 |
| `:P` 立即外设访问 | I_:P 只读不更新映像，Q_:P 只写且同时改映像（p127、p130） | ≠ 换个地址写法，是绕过过程映像直接访问物理点；强制只能强制 :P |
| 一致性数据 | 多字节一次整体刷新、不被扫描/通信中途撕裂（p454–455） | ≠"数值正确"，专指传输的原子性，须显式用一致性指令并脱离自动更新 |
| 三级存储 | 装载≈硬盘、工作≈RAM、保持性≈掉电保留少量运行值（p119–120） | ≠ 笼统"内存"，起始值在装载、当前值在工作，三者分工明确 |
| 保持性（Retain） | 只有显式标记的 M/DB/FB 变量跨掉电保留（p93–94、p120） | ≠"掉电后全部保留"，非保持区暖启动时清零或复位为初值 |
| 诊断缓冲区 | 最多 50 条、仅 10 条永久、满后覆盖最早、掉电保存、MRES 不清除（p123、p1497） | ≠ 完整运行日志，是容量有限的环形缓冲，是排障"第一现场" |
| 优化块访问 | 优化 DB 元素只有符号名、无固定绝对地址，新 DB 默认优化（p208） | ≠ 单纯"存储效率选项"，需绝对寻址的场合必须改标准访问 |
| 智能设备（I-Device） | 自带用户程序预处理、又作为 IO 设备挂到上位控制器的双重角色（p1044–1045） | ≠ 普通主/从，通过 GSD 文件暴露接口以保护专有知识 |
| 工艺对象（TO） | 预置的带组态/调试/诊断 UI 的功能封装，参数在 TO-DB（p751、p754） | ≠ 可直接 new 的软件类，须经项目树添加并下载，重命名后要 STOP 重下载 |
| HSC（高速计数器） | 硬件实现、组态后无需调用即计数，可处理高于扫描速率的脉冲（p631–632） | ≠ 普通计数器指令，后者受扫描速率限制会漏计高频脉冲 |

完整词典见 [GLOSSARY.md](./GLOSSARY.md)。

## 如果只带走三句话

1. **程序结构由 OB 决定，FB 靠背景 DB 实现"实例"**——OB 是事件入口不是函数，背景 DB 不是私有数据；这两点搞错，程序会在最意想不到的地方丢数据或错响应。
2. **实时性以扫描周期计，一致性要显式保障**——高频事件用 HSC、恒速任务用循环中断 OB；多个相关值必须用 DIS_AIRT/EN_AIRT 包住临界区，否则读到的是被中断切开的"撕裂"数据。
3. **手册的保守是刻意的**——24V 电源绝不与传感器电源并联、安全必须由独立于 PLC 的急停兜底、排障先读诊断缓冲区、插卡前先确认 CPU 在 STOP。这些"硬规则"比任何技巧都值钱，因为它们守的是设备与人的安全底线。
